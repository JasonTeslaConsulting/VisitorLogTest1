# Application build plan

One directory per application build, holding the plan an autonomous build session works from.

```
docs/plan/
  README.md          this file
  app.md             ONE per application — written once, then read-only
  units/<NNN>-<slug>.md   one file per build unit (one page or one shared foundation)
  ROADMAP.md         GENERATED — npm run docs:plan
```

## Why one file per unit

Same reasoning as `src/routes/modules/`, sharded `src/types/`, and `docs/features/`: only that
unit's own branch ever writes its file, so two units in flight never conflict on the plan itself.
`ROADMAP.md` is the one conflictable file, and it inherits `docs/architecture/inventory.md`'s exact
recipe — see its own header comment.

## `app.md` is shared but not a hotspot

It is written once, on a `docs/<initials>-plan-<app>` branch, **before any unit branch exists**,
then treated as read-only for the rest of the build. A mid-build change to the entity model, roles,
or nav map is a new `docs/` PR, not a drive-by edit on a unit branch.

## `status:` in a unit's frontmatter is local resume state — not a cross-developer signal

A unit's `status` (`draft → spec-ready → approved → building → pr-open`, or `blocked`) tells an
orchestrator session how to resume its own work after a crash, compaction, or restart. It is
**not** how other developers see what's claimed or shipped — a status flipped on an unmerged branch
is invisible to everyone else until that branch merges, which is exactly the flaw `docs/wip/` has on
its own.

**There is deliberately no `done` status.** Whether a unit has shipped is *derived*, never stored:
every unit's squash-merge subject is prefixed `[U003]` (see `CONTRIBUTING.md`), so
`git log origin/main --oneline --grep '^\[U003\]'` answers it authoritatively. This removes the only
cross-unit write the design would otherwise need — no branch ever reaches over to edit another
unit's file to mark it done.

Cross-developer truth for **in-flight** work is the remote branch namespace
(`git ls-remote --heads origin 'refs/heads/unit/*'`) plus each in-flight unit's frontmatter read
directly off `origin/main` — never the local working tree. See `.claude/skills/build-app/SKILL.md`
and `.claude/skills/resolve-conflicts/SKILL.md` for how a build session and a conflict resolution
use this.

## No remote configured yet

`build-app` works fully locally before Phase 0b (git remote, `gh`/`tea`) is done — see
`docs/PREFLIGHT.md`. With no `origin`, each unit is squash-merged straight into local `main` once
VERIFY passes, instead of opening a PR someone would otherwise merge by hand: the GATE step already
served as the review before any code was written, so there's no reviewer being bypassed. It uses
the same `[U0NN] <unit title>` commit-subject convention a real squash-merge PR would produce, which
is exactly why `scripts/gen-plan-docs.mjs`'s `isMerged()` already prefers `origin/main` but falls
back to local `main` when there's no remote — the two pieces are designed together. This is a live
`git remote -v` check on every unit, not a stored setting, so adding a real remote mid-build changes
the very next unit's behavior automatically. See `.claude/skills/build-app/SKILL.md`'s "PUSH AND
PR" section for the exact commands.

## `ROADMAP.md`

Generated by `npm run docs:plan` from committed state only (unit frontmatter + `git log
origin/main`) — never from live remote refs, so `npm run docs:plan -- --check` never fails
nondeterministically in CI. Shows progress counts, build order, what's ready to build now, what's
blocked, and any schema/dependency errors. Regenerate and commit after every unit-file change; CI
blocks on it being stale, the same way it blocks on `docs/architecture/inventory.md`.

`npm run plan:next` prints one line — the next buildable unit's id, path, and status — so a cold
orchestrator session (or a human) can bootstrap without reading every unit file.

## Where this comes from

Don't hand-write `app.md` or a unit file. `.claude/skills/plan-app/SKILL.md` conducts the app-level
interview and writes `app.md` plus a first batch of `draft` units. `.claude/skills/spec-page/
SKILL.md` fills in a `draft` unit's body just before it's built. `.claude/skills/build-app/
SKILL.md` reads `npm run plan:next` and drives the build loop from there.
