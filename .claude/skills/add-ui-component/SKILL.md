# Skill: Add a UI Component

Read this entire file before writing any code.

## What this skill covers

Adding a new reusable component to `platform/src/components/ui/`. This covers two cases:

1. Customizing a shadcn-generated primitive directly (adding props, fixing a default, adjusting
   styling) — this folder is the shadcn scaffold and the customized library in one place, so
   there's no wrapper indirection anymore
2. A custom component that shadcn doesn't have

**If you are building an app from this skeleton (not developing the skeleton itself): do not
follow this skill** — `platform/src/components/ui/` is frozen for consuming projects; add page-scoped
components in `src/components/<PageName>/` instead.

---

## Decision — do you need a new UI component?

Ask: will this component be used in more than one page?

- Yes → `platform/src/components/ui/`
- No → `src/components/<PageName>/` (page-scoped, not shared)

---

## File location and naming

```
platform/src/components/ui/<component-name>.tsx   ← kebab-case for shadcn-derived primitives
platform/src/components/ui/<ComponentName>.tsx    ← PascalCase for custom/composed components
```

No naming collisions to worry about — a shadcn primitive and its customizations live in the same
file under its own name (`select.tsx` exports `Select`), there's nothing to disambiguate from.

---

## Case 1 — Customizing a shadcn-generated primitive

Purpose: add a prop, fix a default, or adjust styling directly on the generated component — it's
ordinary project code once generated, not something to wrap.

```tsx
// platform/src/components/ui/select.tsx
// Generated by `npx shadcn@latest add select`, then customized: SelectTrigger's fill
// uses bg-input-background instead of the generated bg-background default.

const SelectTrigger = React.forwardRef<...>(({ className, children, ...props }, ref) => (
  <SelectPrimitive.Trigger
    ref={ref}
    className={cn(
      "flex h-10 w-full items-center justify-between rounded-md border border-input bg-input-background px-3 py-2 text-sm ...",
      className,
    )}
    {...props}
  >
    {children}
    ...
  </SelectPrimitive.Trigger>
));
```

Document the *why* for any non-obvious customization in a short comment at the top of the file —
the next person editing it needs to know it diverges from a plain `shadcn add` output and why.

## Case 2 — Custom component (no shadcn equivalent)

Build with shadcn primitives where possible. Use shadcn CSS variables for all colors.

```tsx
// platform/src/components/ui/StatusBadge.tsx
import { cn } from "@framework/lib/shadcn/shadcn-utils";

type Status = "active" | "inactive" | "pending";

const STATUS_STYLES: Record<Status, string> = {
  active: "bg-success/10 text-success-text dark:bg-success/20",
  inactive: "bg-muted text-muted-foreground",
  pending: "bg-warning/10 text-warning-text dark:bg-warning/20",
};

type StatusBadgeProps = {
  status: Status;
  className?: string;
};

export const StatusBadge = ({ status, className }: StatusBadgeProps) => {
  return (
    <span
      className={cn(
        "inline-flex items-center px-2.5 py-0.5 rounded-full text-xs font-medium",
        STATUS_STYLES[status],
        className,
      )}
    >
      {status.charAt(0).toUpperCase() + status.slice(1)}
    </span>
  );
};
```

## Rules

- Named export only — no `export default`
- Always support a `className` prop for overrides
- Use shadcn CSS variables for colors — never hardcode hex or Tailwind static colors
- Never hardcode spacing — use the 4px base-unit scale (`space-1`…`space-16`, i.e. Tailwind's
  `1`/`2`/`3`/`4`/`6`/`8`/`12`/`16` steps: 4/8/12/16/24/32/48/64px). The `StatusBadge` example
  above predates this rule and uses `px-2.5`/`py-0.5` (10px/2px, off that scale) — don't copy those
  values into new components, even though the example itself is left as-is
- Components must work in both light and dark mode
- Props should be typed explicitly — no `any`

## On completion

A component nobody can find gets rebuilt by the next session. Three of these steps were skipped
often enough to leave real debris: the Primitives page carried a "No distinct Tag/Chip component
exists yet" placeholder for the entire life of the repo, and `command.tsx` sat in `ui/` with zero
importers until someone went looking.

- **Add a live demo** to the right sample page: a form-level control goes on
  `platform/src/samples/Primitives.tsx`, a page-fragment composite on
  `platform/src/samples/AdvancedComponents.tsx`. Demo more than one state — resting plus whichever
  states the component can get *wrong* (empty, error, disabled, overflowing)
- **Register its id in that page's `SECTIONS` array** and render the section in the same position.
  The array drives the in-page nav; the two disagreeing is silent
- **If it retires a `Placeholder`,** delete the placeholder in the same commit
- **Add an entry to `docs/architecture/ui.md`** — via `platform/materialized/docs/architecture/ui.md`
  then `npm run framework:apply`. Say *why*, not just what: the constraint that shaped it, and
  anything a reader would otherwise "fix" back
- **If it was generated by `npx shadcn add`,** list every customization in the file header (see
  `field.tsx` and `combobox.tsx`) — that header is the only thing standing between a future
  `--overwrite` and silently losing the divergences
- `npm run docs:arch`, then `npm run framework:lock`

---

## What NOT to do

- Do not use `export default`
- Do not hardcode colors (`bg-white`, `text-gray-900`, `#ffffff`)
- Do not create page-specific components here — those go in `src/components/<PageName>/`
